# 莎士比亚迷你搜索引擎成员一报告内容

## 第 1 章 问题描述与语料准备

### 1 1 项目目标与成员一职责

本项目针对 MIT 网站的 The Complete Works of William Shakespeare 构建迷你搜索引擎。系统需要统计语料词频，解释并剔除停用词，通过词干化构造倒排索引，接受单词或短语查询并返回文档 ID，最终分析阈值对查询结果的影响。

成员一负责语料范围与文档 ID、正文清洗、分词和原词形 TF/DF 统计、停用词筛选、共享词干化预处理模块及相关正确性验证，并提供规模扩展分析。成员二负责倒排索引，成员三负责查询程序与固定索引上的查询阈值实验。

### 1 2 数据版本与文档粒度

语料使用 TheMITTech/shakespeare 的固定版本 `6b82db852c7322dd33e95db347f0ddfc812c6409`，原始获取日期为 2026-10-09。本次处理日期为 2026-10-14。参考来源见根目录 `REFERENCES_A.md`。

我们从主页列出的作品入口出发，戏剧按场景、十四行诗按首、其他诗作按篇划分文档。最终包含 37 部戏剧的 754 个场景、154 首十四行诗和 4 篇其他诗作，共 912 篇。选择场景页后排除对应整剧页，并排除目录、导航与旧版重复目录，从而避免重复计数。

文档按来源相对路径的 Ordinal 顺序确定稳定 ID。正式文档映射包含 doc_id、work_title、source_url、clean_path。已归档 951 个唯一网页，即 912 个正文来源和 39 个目录来源，并保存逐文件 SHA256。正式清洗文本的内容哈希均不同。

### 1 3 正文范围与清洗规则

戏剧保留台词与舞台说明，排除说话人标签、网页标题、场景标题和导航。诗歌保留诗节，排除前置题献、编辑说明及 Argument；Venus and Adonis 从 `EVEN as the sun` 的首节开始，Elegy 从诗行 table 提取。按照指定网站目录收录 Elegy，不把站点归类当作本项目对作者归属的判断。

原站点存在缺少闭合 blockquote 的页面，仅按标签嵌套深度截取会引入页尾导航。我们在独立复核中发现此问题，随后将新台词锚点和导航 table 加入提取边界，并增加缺失闭合标签的回归用例；最终所有正文均不含 `Shakespeare homepage` 导航字符串。

原始字节保持不变，清洗文本使用 ASCII 子集的 UTF-8。非 ASCII 源字符作为分隔符处理。这是面向该英文语料的简化，不是通用多语种清洗方案。

## 第 2 章 成员一的数据结构与算法

### 2 1 分词与位置定义

分词规则为 `[A-Za-z]+`，统一转为 ASCII 小写。数字、标点、撇号和连字符作为分隔符。例如 `King's` 产生 `king, s`，`ne'er` 产生 `ne, er`。该规则简单且可复现，同时会把古英语缩写拆开；因此把常见片段 s、t、d 等列入人工审查的功能词候选，并在报告中明确此限制。

每篇清洗正文的词位从 0 开始，先分词、计词位，再判断停用词。过滤后的词位不重编号。例如 `The king runs and walks` 的五个原始位置是 0 至 4；使用测试停用词 a、the、and 后输出 king[1]、run[2]、walk[4]。这种位置保留是连续短语核验的前提。

### 2 2 词频与文档频率

设文档数为 D，总词次为 T，某个规范化原词形 w 的总出现次数为 TF(w)，出现过 w 的不同文档数为 DF(w)。定义：

```text
词次占比 r_tf(w) = TF(w) / T
文档覆盖率 r_df(w) = DF(w) / D
```

统计使用开放寻址哈希表，约 0.7 装载率扩容。每项存储词字符串、TF、DF 和 last_doc 等字段。按文档 ID 依次读取时，相同词在同一文档内只增加 TF；last_doc 改变时才增加 DF。统计结束后按 TF 降序输出，同频词按字母序排列。

最终在 912 篇清洗文档中得到 T = 909,915，原词形种类 V = 23,524。以下是部分实际结果，统计发生在去停用词与词干合并之前。

| 原词形 | TF | DF | 文档覆盖率 |
| --- | ---: | ---: | ---: |
| the | 29,122 | 891 | 97.70% |
| and | 27,311 | 905 | 99.23% |
| not | 8,865 | 814 | 89.25% |
| thou | 5,861 | 657 | 72.04% |
| good | 2,930 | 608 | 66.67% |
| love | 2,335 | 542 | 59.43% |
| king | 1,717 | 355 | 38.93% |
| queen | 562 | 186 | 20.39% |

预期计数时间为 O(T)，排序输出为 O(V log V)。设单篇文档最大长度为 L_max，当前实现主要空间为全词汇哈希表 O(V) 与一篇文本、token 数组 O(L_max)，不是把全部文档的原始 token 同时保存在 A 的计数器中。B 的构建器另有其全量 token 内存开销。

### 2 3 有意义词与噪声词的分界

高频不等于无意义。love、good、king 等词即使覆盖较多文档，也能反映主题或人物；not、no、nor 表达否定，删除后可能改变查询含义。我们保留这些词。

最终规则同时要求：人工确认属于功能词候选、达到词次占比下限、达到文档覆盖率下限。人工候选保存在 `config/function_words.txt`，筛选过程与每个词的判断保存在 `results/preprocess/stopword_decisions.tsv`。这使阈值依据可以追溯，而不是直接套用通用停用词表或简单删除排名前若干个词。

三组实验在同一语料、同一文档粒度和同一人工候选范围下进行：

| 策略 | 最低词次占比 | 最低文档覆盖率 | 停用词数 | 删除词次 | 保留词位 | 删除比例 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 保守 | 0.10% | 50% | 76 | 430,548 | 479,367 | 47.3174% |
| 默认折中 | 0.05% | 25% | 89 | 441,143 | 468,772 | 48.4818% |
| 激进 | 0.01% | 10% | 100 | 444,342 | 465,573 | 48.8334% |

默认采用折中策略，其结果保存为 `config/stopwords.txt`。相较保守策略，多排除 13 个功能词及 10,595 个词次；进一步改为激进策略只多删除 3,199 个词次，收益较小，但会扩大不可直接检索的词形范围。因此默认方案在索引规模与查询保留之间作出折中。这个分界是明确记录的工程选择，不是对所有检索任务唯一正确的判断。

### 2 4 词干化与对外接口

词干化使用 Martin Porter 本人提供的 thread-safe ANSI C Release 4。保留原始完整源码、独立模块及官方 23,531 组输入输出，出处与使用说明均在参考资料中列出。Porter 是词干算法，并非语义词形还原，例如 runs → run、walked → walk、does → doe。

核心顺序是规范化原词形 → 判断停用词 → 对剩余词进行词干化。`data/tokens.tsv` 严格使用 B 已约定的 doc_id、position、stem 三列。默认输出 468,772 行词位；经 B 构建与合并后得到 14,590 个不同词干。

必须区别“原词形停用词”和“词干”。默认方案中 having 不属于最终停用词，但会归为 have；its 保留后会归为 it。若 B 再对词干套用原词形停用词表，会误删这些有效位置。所以 A 已过滤的 tokens 传入 B 时，stopwords_path 传 NULL。

共享接口 `ads_pp_process` 同时服务查询。普通查询选择 keep_stopwords=0；短语核验选择 1，以便按实词词干、停用词原词形及原始位置比较窗口。调用方拥有返回的 token 列表并负责释放。文档路径、规则版本和停用词配置必须与建索引时相同。

### 停用词阈值对可查询结果的影响

以下结果由三套真实 tokens 分别构建 B 索引后测得。输入经各策略的共享预处理归一化，数字为命中文档数；被认定为停用词的单词输入返回空结果。

| 查询 | 保守 | 默认折中 | 激进 |
| --- | ---: | ---: | ---: |
| king | 377 | 377 | 377 |
| queen | 187 | 187 | 187 |
| love | 604 | 604 | 604 |
| not | 814 | 814 | 814 |
| thine | 257 | 0 | 0 |
| having | 140 | 140 | 0 |
| the | 0 | 0 | 0 |

主题词与否定词因为人工审查策略而保留；部分代词或功能词在放宽筛选条件后失去单词查询入口。阈值不只影响存储量，也会改变哪些原词形可以形成有效查询。

该实验调整的是**停用词筛选阈值**，改变后重建索引。成员三仍需在固定索引上完成最低词频 t 与多词匹配比例 τ 的实验。两类阈值不能混为同一个自变量。现有输入包没有查询实现，所以这里不宣称完成其全部查询功能，也没有在缺少人工相关性标注时虚报查准率或召回率。

## Bonus 500000 个文件和 400000000 个不同词

### 当前版本是否仍然可用

当前实现不能保证处理这个规模。文档数 D、不同词数 V 与总词次数 T 是三个不同量，至少有 T ≥ V。不能把 400,000,000 个不同词误当作总词次，也不能直接建立 D × V 的稠密矩阵来估算倒排索引。实际成本还取决于平均词长、各词的文档分布和需要保存的位置数量。

在本机 64 位 GCC 构建中，计数器每个 Word 槽位为 48 字节。哈希表装载率约 0.7，容量采用 2 的幂。若 V = 400,000,000，需要 1,073,741,824 个槽位，槽数组约 48 GiB。假设每个词平均 10 个字符再加结束符，词字符串约 4.10 GiB；排序输出所需的 400,000,000 个 8 字节指针又约 2.98 GiB。仅这些项即约 55.08 GiB，尚未包括分配器开销、单篇 token 数组和正文。

扩容时新旧槽数组会短暂同时存在，旧表约 24 GiB、新表约 48 GiB，仅槽数组峰值已达 72 GiB；再加字符串等，峰值更高。B 的当前构建和加载还会把全部词位及倒排结构放入内存。因此“计数器用了哈希表”或“用了磁盘保存文件”都不能证明整个系统能处理该规模。

ID 的数值范围与内存容量是两回事：500,000 个文档约需 19 位 ID，400,000,000 个词约需 29 位 ID，均可使用 uint32_t；总词次、词位和文件偏移应使用 uint64_t。32 位 ID 足够并不能解决几十 GiB 的内存结构问题。

### 需要的外存改造

1. 将正文与分词改为流式处理，跨块保存未结束词和当前文档词位；不能对每个块重新从位置 0 计数。
2. 第一遍统计采用固定内存上限。块内聚合 `(原词形, doc_id, 局部TF)`，写出排序临时段；多路归并同一原词形与文档的记录后求全局 TF 和 DF。一个文档可能跨多个块，DF 必须按合并后的不同 doc_id 去重，不能直接累加块内 DF。
3. 根据全局统计确定停用词。第二遍读取正文，先过滤原词形再词干化，输出 `(stem, doc_id, position)`；内存到达上限就写有序段，再多路归并。不同原词形可能归并为同一词干，因此这一阶段仍须按词干重新排序与合并。不可重读的输入需落盘缓存，成本需单独计算。
4. 将词典与倒排表分别保存。词典采用磁盘有序结构或稀疏索引，只缓存一部分块；每个词记录倒排块的偏移和长度。doc_id 与词位可用差分及变长编码，查询时按需解压，并使用跳跃信息减少无用读取。
5. 根据内存和磁盘吞吐量设置分片。按词干哈希分片可稳定路由词项，多词查询需要合并文档集合；查询缓存、配置版本和各分片词干化规则必须一致。短语仍需保存原始词位及可核验的完整正文或规范化词序列。
6. 明确 I/O、磁盘容量与临时段数量的预算，分阶段测峰值内存、吞吐量和查询延迟，并支持失败后继续归并。

关键流程如下：

```text
第一遍正文流
  -> 内存限额内聚合 (surface, doc_id, local_tf)
  -> 外排临时段
  -> 多路归并同一 surface 和 doc_id
  -> 全局 TF 与去重 DF -> 固定 stopwords

第二遍正文流
  -> 维护原始词位 -> surface 去停用词 -> Porter stem
  -> 外排 (stem, doc_id, position) 段
  -> 多路归并 -> 压缩磁盘倒排块与可定位词典
```

假设总中间记录为 R、单块可容纳 M 条记录、归并扇入为 k，外排首先产生约 ceil(R/M) 个段，归并阶段需要约 ceil(log_k(ceil(R/M))) 轮；每轮都要读取和写出相关记录。内存可以限制在块与归并缓冲区大小，但不能据此忽略多轮 I/O 和临时磁盘成本。

### 实测证据与边界

`scripts/benchmark_A.ps1` 构造一篇测试文档，分别包含 1,000、10,000、100,000 个不同纯字母词，每词恰好出现一次；调用同一个 C 计数器，并检查输出词数、TF=1、DF=1。一次本机测量如下，原始数据见 `scale_benchmark.tsv`。

| 文档数 | 不同词数 | 总词次 | 墙钟时间秒 | 采样到的峰值工作集 MiB |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,000 | 1,000 | 0.079921 | 4.62 |
| 1 | 10,000 | 10,000 | 0.072258 | 5.54 |
| 1 | 100,000 | 100,000 | 0.165877 | 27.92 |

这是词汇增长实验，内存包含进程、正文、token 数组与哈希表。小样本时间受进程启动和计时粒度影响，不能把前两行解释为数据越大程序越快；采样峰值也不是逐分配的精确内存上界。

这个实验没有模拟 500,000 个独立文件或 400,000,000 个不同词。它验证了当前计数器在已测规模上的行为，并与结构级内存估算相互支持；外存方案目前是明确的改造设计，不能写成已经在目标规模运行成功。
